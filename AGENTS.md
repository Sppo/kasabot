# AGENTS.md — Процес роботи AI-агентів у проєкті KasaBot

Цей файл визначає робочий процес агента в репозиторії **KasaBot** та узгоджує проєктні вимоги з глобальним `~/.claude/CLAUDE.md`.

---

## 1. Контекст сесії (Що читати на старті)
1. **Обов'язково на старті сесії:**
   - **[ARCHITECTURE_RULES.md](./ARCHITECTURE_RULES.md)** — усі технічні, архітектурні та безпекові правила (`NEVER / ALWAYS`). Цей файл не дублює їх, а посилається на них як на закон.
   - **[PLAN.md](./PLAN.md)** — поточна активна задача, архів виконаних планів та дорожня карта.
2. **За потреби (коли задача стосується вимог, схеми БД, API чи білінгу):**
   - **[SPEC.md](./SPEC.md)** — повна технічна специфікація (схема таблиць, ендпоінти, мобільний UX).
   - **[GUIDE.md](./GUIDE.md)** — продуктова логіка («ввід за 3 секунди») та стратегія монетизації / App Store.

## 2. Узгодження з глобальним `CLAUDE.md` (Пріоритет та Явні Дозволи)

У межах репозиторію **KasaBot** діють усі правила безпеки та мінімального diff із глобального `CLAUDE.md` з такими **явними проєктними дозволами** (підтвердження плану користувачем автоматично дає дозвіл на ці дії):

1. **Дозволені команди перевірки (`make check`):**
   - Після внесення змін за планом агент **має право і зобов'язаний** запускати команди компіляції та тестів: `go build ./...`, `go vet ./...`, `go test ./...` та `npm run build` (або `npx tsc --noEmit`) у папці `web/`.
   - Заборона з глобального `CLAUDE.md` залишається чинною для фонових dev-серверів (`npm run dev`, `vite`), встановлення нових пакетів поза планом та будь-яких `git`-команд (крім безпечного читання під час код-ревю, див. п. 4) — їх без окремого дозволу не запускати.
2. **Дозволені конфіги та міграції в межах затвердженого плану:**
   - Якщо це вказано у підтвердженому користувачем плані задачі, агенту **дозволено** редагувати `.env.example`, `web/.env.example`, `go.mod`, `package.json`, а також додавати нові міграції в `Migrations()` та сіди в `OnWorkspaceCreated`.
   - Реальний локальний `.env` із секретами та вже застосовані старі міграції змінювати без окремого дозволу **заборонено**.
3. **Дозволені архітектурні інтерфейси:**
   - Інтерфейс `Repository` у кожному модулі (`internal/modules/<name>`) та інтерфейси ядра (`core.Module`, `core.AIClient`) є **обов'язковим винятком** із глобального правила «не створюй інтерфейси наперед». Вони необхідні для фізичної ізоляції `service.go` від `database/sql` та написання unit-тестів (`service_test.go`).
4. **Git під час код-ревю (тільки читання, без окремого дозволу):**
   - Під час код-ревю дозволено запускати будь-які `git`-команди, які **не змінюють** робоче дерево, індекс, історію чи гілки: наприклад, `git status`, `git diff`, `git log`, `git show`, `git blame`, `git branch --list`, `git ls-files`, `git rev-parse`. Додатково питати дозволу не потрібно.
   - **Заборонено** все, що змінює стан: `add`, `commit`, `push`, `pull`, `fetch` зі зміною посилань, `merge`, `rebase`, `checkout`, `switch`, `restore`, `reset`, `clean`, `stash`, `cherry-pick`, створення чи переключення гілок, редагування `.git/`.
   - Усі команди виконуються **лише в межах цього репозиторію**: не переходь у інші каталоги, не чіпай інші репозиторії та файли поза проєктом.
   - Якщо під час ревю знайдено щось термінове чи критичне і потрібно щось змінити — спочатку запитай користувача.
5. **Залежності та сервіси (замість заборонного списку):**
   - Нові бібліотеки та сервіси (зокрема Redis, ORM чи фронтенд-бібліотеки) дозволені, якщо вони (1) вирішують реальну задачу затвердженого плану, (2) не ламають існуючі інваріанти (шари, `workspace_id`, `arch_test.go`), (3) названі в плані з однорядковим обґрунтуванням. Затвердження плану користувачем є дозволом на перелічені в ньому залежності.
   - Інфраструктурні сервіси (Redis, PostgreSQL тощо) додатково фіксуються в [SPEC.md](./SPEC.md).
   - ORM та query builder дозволені лише якщо фільтр `workspace_id` лишається видимим у коді та перевіряється тестом.
   - Поза межами затвердженого плану глобальна заборона на встановлення, оновлення й видалення залежностей лишається чинною.

## 3. Режими роботи: Швидкий шлях (Fast-Track) vs 5-кроковий План

Дотримуйся режимів за формулюванням із глобального `CLAUDE.md` (*«проаналізуй»* — тільки аналіз; *«надай план»* — тільки план; *«зроби / поправ»* — дія за правилами нижче):

### А. Швидкий шлях для дрібних правок (Fast-Track — без файлу в `plans/`)
Якщо користувач прямо просить *«поправ / зроби»* тривіальну точкову правку, яка одночасно відповідає **всім** умовам:
- зачіпає **`≤ 2` файли**;
- **не змінює** схему БД, міграції, контракти REST API, архітектуру шарів чи залежності (наприклад: опечатка, дрібний фікс верстки/тексту, локальний баг в одній функції).

**Дія:** Не створюй бюрократичний файл у `plans/`. Коротко напиши, що змінюєш, внеси точковий патч, прожени перевірку (`go test ./...` / `npm run build`) і дай стислий підсумок.

### Б. Стандартний 5-кроковий процес для задач і фіч (`plans/` → `plans/archive/`)
Для всіх нових етапів, фіч, модулів, змін БД/API або задач на `> 2` файли **заборонено** писати код без затвердженого плану:

1. **Крок 1 — Аналіз:** Досліди пов'язані файли, [ARCHITECTURE_RULES.md](./ARCHITECTURE_RULES.md) та [SPEC.md](./SPEC.md). Для багу — знайди точну першопричину (root cause). Якщо є неоднозначність — запитай.
2. **Крок 2 — Файл плану:** Створи `plans/<NNN>-<short-name>.md` за шаблоном [plans/TEMPLATE.md](./plans/TEMPLATE.md) зі статусом `Чернетка — очікує підтвердження` і пропиши посилання на нього в [PLAN.md](./PLAN.md) («Поточна активна задача»).
3. **Крок 3 — Підтвердження (STOP & ASK):** Коротко покажи суть плану в чаті та запитай: *«План створено в `plans/NNN-...md`. Починаємо реалізацію?»*. Чекай на відповідь.
4. **Крок 4 — Виконання та перевірка:** Виконай план і запусти `make check` (`go vet ./...`, `go test ./...` вкл. з `arch_test.go`, `go build ./...`, `npm run build`). **Не став статус `Виконано — очікує перевірки користувачем` і не відмічай `[x]`, поки `make check` не пройшов без помилок.** Якщо перевірка падає — виправ причину в межах плану, а якщо не виходить — зупинись і повідом користувача, що саме падає. **Сам в архів не перенось!**
5. **Крок 5 — Архівування (після команди користувача «перенеси план в архівні»):**
   - Зміни статус плану на `Закрито / В архіві` і перемісти файл у `plans/archive/<NNN>-<short-name>.md`.
   - Прибери тимчасово закоментований у межах цієї задачі старий код (якщо користувач підтвердив, що нова логіка працює).
   - Онови чекбокси дорожньої карти і таблицю архіву в [PLAN.md](./PLAN.md), очистивши блок «Поточна активна задача».

## 4. Стандарти коду, коментарів та звітності

1. **Мова коду та коментарів:**
   - Усі ідентифікатори в коді (змінні, функції, структури, таблиці, JSON-поля, коди помилок) — **англійською мовою**.
   - Коментарі в коді — **українською мовою**, короткі й природні (від імені розробника проєкту, без згадок про AI чи прохання користувача).
   - Спілкування з користувачем — **українською мовою**, чітко і по суті.
2. **Життєвий цикл закоментованого коду:**
   - Під час створення нових модулів з нуля не залишай мертвий чи чернетковий закоментований код.
   - При модифікації вже існуючої бізнес-логіки старий варіант можна тимчасово закоментувати з технічним поясненням (згідно з глобальним `CLAUDE.md`) і видалити його під час Кроку 5 (архівації плану) після перевірки користувачем.
3. **Баги поза межами задачі (Out-of-Scope Issues):**
   - Якщо під час роботи ти помітив баг, порушення архітектури або техборг у файлі, який не стосується поточної задачі — **не виправляй його мовчки** (щоб не роздувати diff). Обов'язково опиши знахідку окремим пунктом у фінальному підсумку.
4. **Формат підсумку після виконання задачі:**
   - Що змінено і в яких файлах (із клікабельними посиланнями).
   - Результат `make check` (`go vet`, `go test` вкл. з `arch_test.go`, `go build`, `npm run build`): встав фактичний фінальний вивід команди (наприклад, рядки `ok ...` та код виходу), а не лише слова «все пройшло». Окремо вкажи, що саме треба перевірити вручну.
   - Що свідомо не змінювалось / знайдені проблеми поза межами задачі.
5. **Коміти (тільки за явним дозволом користувача):**
   - Повідомлення коміту має бути максимально зрозумілим: короткий заголовок (що змінено), а за потреби кілька рядків про причину зміни. Пиши так, як це написала б людина-розробник проєкту.
   - **Пряма команда користувача в чаті є дозволом.** Якщо користувач пише «коміт», «коміт і пуш», «закоміть і запуш», «commit and push», агент виконує саме це і **не перепитує** дозволу окремо на `git add`, `git commit` чи `git push`. Без такої команди коміти та пуш не робити.
   - **Межі пуша:** `git push` лише поточної гілки в її існуючий upstream, без `--force` / `--force-with-lease`, без створення чи пуша інших гілок і тегів. Якщо пуш відхилено (наприклад, віддалена гілка попереду), зупинись і повідом користувача, а `pull`, `rebase` чи `merge` без окремого дозволу не виконуй.
   - **Що додавати в коміт:** лише файли поточної задачі. Ніколи не додавай `.env`, `logs/`, ключі та інші секрети; перед комітом перевір `git status`, що їх у списку немає.
   - **Без жодних позначок про AI:** не додавай `Co-Authored-By: ...`, `Generated with ...`, згадок Claude, Gemini чи іншого агента або інструмента, ні в заголовку, ні в тілі, ні у футері. Це стосується і описів PR.
